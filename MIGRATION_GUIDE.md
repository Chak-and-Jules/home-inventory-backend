# Google Cloud Platform (GCP) Migration Guide

This document outlines the strategy, trade-offs, step-by-step procedure, local development configuration, and Infrastructure as Code (IaC) templates for migrating the **Home Inventory System** from Supabase (Auth + Storage) and Vercel (Frontend) to **Google Cloud Platform** (Cloud Identity Platform, Cloud Storage, and Cloud Run), while retaining PostgreSQL on Supabase.

---

## 1. Architectural Overview & Migration Plan

### Target Architecture
- **Frontend**: Next.js App / React hosted on **Google Cloud Run** (Containerized Docker deployment).
- **Backend**: Go API hosted on **Google Cloud Run** (Existing setup via Google Cloud Build).
- **Authentication**: **Google Cloud Identity Platform** (GCIP / Firebase Auth) with Email/Password authentication as well as OAuth support for Google, Apple, and Facebook logins.
- **File Storage**: **Google Cloud Storage (GCS)** public bucket with pre-signed upload URLs generated by the backend API.
- **Database**: PostgreSQL on **Supabase** (Unchanged).
- **CI/CD**: **Google Cloud Build** triggers configured for backend (`main` branch) and frontend repositories.

---

## 2. Pros and Cons (Good and Bad Outcomes)

### Positive Outcomes (Pros)
1. **Unified Infrastructure & Operations**:
   - Centralized logging, IAM permissions, metrics, monitoring, and billing under a single GCP Project console.
2. **Identity & Authentication Control**:
   - Google Cloud Identity Platform (GCIP) provides enterprise-grade SLA, tenant management, built-in rate limiting, and seamless social provider integration (Google, Apple, Facebook) as well as traditional Email/Password authentication.
3. **Scalability & Billing Predictability**:
   - Cloud Run auto-scales down to zero instances when idle, minimizing costs during low-traffic periods while handling traffic spikes automatically.
   - GCS provides cost-effective, durable storage with fine-grained IAM control and pre-signed upload capabilities.
4. **Consistency across Environments**:
   - Running Next.js inside a Docker container on Cloud Run guarantees identical runtime behavior between local, staging, and production environments.

### Potential Drawbacks & Risks (Cons / Trade-offs)
1. **Loss of Vercel Edge/CDN Optimization**:
   - Vercel offers global Edge caching out of the box. Cloud Run runs in a specific GCP region (e.g., `us-central1` or `europe-west1`), which may slightly increase TTFB for global users unless Cloud CDN + Global HTTP(S) Load Balancer is added in front (adds minor cost).
2. **Cold Starts**:
   - Cloud Run services scaled to 0 instances experience a brief latency penalty (1-3s) on the first request after a period of inactivity. Setting `min-instances = 1` eliminates cold starts but incurs continuous minimal compute cost.
3. **Egress & Storage Costs**:
   - While GCP has a generous free tier (e.g., 2 million requests/month on Cloud Run, 5 GB storage on GCS), standard network egress fees apply beyond free limits.
4. **Migration Effort**:
   - JWT validation logic in the Go backend must be updated to verify GCIP (Firebase Auth) tokens instead of Supabase JWTs.

## 3. Local Development Environment (Zero-Cloud Isolation)

To ensure developers can build and test locally without requiring GCP credentials or accessing live GCP objects:

### Local Auth Strategy (`APP_ENV=local`)
- **Backend Middleware**: When `APP_ENV=local` is set in `.env`, the Go backend bypasses external JWKS/GCIP network calls.
- **Mock Token / Header**: Accepts test Bearer tokens or reads `X-Mock-User-ID` / `X-Mock-Email` headers, populating Gin's context (`userID` and `email`) with pre-configured UUIDs (e.g., matching local test user IDs).

### Local Storage Strategy (`APP_ENV=local`)
- **Local Disk Fallback**: Product image uploads (`POST /api/v1/storage/upload-url` or direct upload) store files in a git-ignored local directory (e.g., `./.uploads/<home_id>/<file_uuid>.jpg`).
- **Local File Serving**: In local mode, the backend serves static assets directly from `./.uploads` under `http://localhost:8080/uploads/...`.

## 4. Terraform Configuration (IaC)

Below is the complete Terraform setup (`main.tf`) to provision the required GCP resources.

```hcl
# main.tf
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 5.0"
    }
  }
}

variable "gcp_project_id" {
  type        = string
  description = "GCP Project ID"
}

variable "region" {
  type        = string
  default     = "us-central1"
  description = "GCP Deployment Region"
}

provider "google" {
  project = var.gcp_project_id
  region  = var.region
}

# Enable required GCP APIs
resource "google_project_service" "identitytoolkit" {
  service = "identitytoolkit.googleapis.com"
}

resource "google_project_service" "storage" {
  service = "storage.googleapis.com"
}

resource "google_project_service" "run" {
  service = "run.googleapis.com"
}

resource "google_project_service" "cloudbuild" {
  service = "cloudbuild.googleapis.com"
}

# Cloud Storage Bucket for Product Images
resource "google_storage_bucket" "product_images" {
  name                        = "${var.gcp_project_id}-product-images"
  location                    = var.region
  force_destroy               = false
  uniform_bucket_level_access = true

  cors {
    origin          = ["*"]
    method          = ["GET", "PUT", "POST", "DELETE", "HEAD", "OPTIONS"]
    response_header = ["*"]
    max_age_seconds = 3600
  }
}

# Allow Public Read Access to Product Images Bucket
resource "google_storage_bucket_iam_member" "public_read" {
  bucket = google_storage_bucket.product_images.name
  role   = "roles/storage.objectViewer"
  member = "allUsers"
}

# Cloud Run Service for Backend API
resource "google_cloud_run_v2_service" "backend" {
  name     = "home-inventory-backend"
  location = var.region
  ingress  = "INGRESS_TRAFFIC_ALL"

  template {
    containers {
      image = "gcr.io/${var.gcp_project_id}/home-inventory-backend:latest"
      env {
        name  = "APP_ENV"
        value = "production"
      }
      env {
        name  = "GCP_PROJECT_ID"
        value = var.gcp_project_id
      }
      env {
        name  = "GCS_BUCKET_NAME"
        value = google_storage_bucket.product_images.name
      }
    }
  }
}

# Allow Public Unauthenticated Invocation for Backend Cloud Run
resource "google_cloud_run_v2_service_iam_member" "backend_public" {
  project  = var.gcp_project_id
  location = var.region
  name     = google_cloud_run_v2_service.backend.name
  role     = "roles/role.invoker"
  member   = "allUsers"
}

# Cloud Run Service for Frontend Web App
resource "google_cloud_run_v2_service" "frontend" {
  name     = "home-inventory-web"
  location = var.region
  ingress  = "INGRESS_TRAFFIC_ALL"

  template {
    containers {
      image = "gcr.io/${var.gcp_project_id}/home-inventory-web:latest"
      env {
        name  = "NEXT_PUBLIC_API_URL"
        value = google_cloud_run_v2_service.backend.uri
      }
    }
  }
}

# Allow Public Unauthenticated Invocation for Frontend Cloud Run
resource "google_cloud_run_v2_service_iam_member" "frontend_public" {
  project  = var.gcp_project_id
  location = var.region
  name     = google_cloud_run_v2_service.frontend.name
  role     = "roles/run.invoker"
  member   = "allUsers"
}
```

## 5. `gcloud` CLI Setup Commands

If provisioning manually via `gcloud` CLI instead of Terraform:

```bash
# 1. Set default GCP Project & Region
export PROJECT_ID="your-gcp-project-id"
export REGION="us-central1"
gcloud config set project $PROJECT_ID

# 2. Enable Required APIs
gcloud services enable \
  identitytoolkit.googleapis.com \
  storage.googleapis.com \
  run.googleapis.com \
  cloudbuild.googleapis.com

# 3. Create Cloud Storage Bucket for Product Images
export BUCKET_NAME="${PROJECT_ID}-product-images"
gcloud storage buckets create gs://${BUCKET_NAME} \
  --location=${REGION} \
  --uniform-bucket-level-access

# 4. Grant Public Read Access to the Bucket
gcloud storage buckets add-iam-policy-binding gs://${BUCKET_NAME} \
  --member="allUsers" \
  --role="roles/storage.objectViewer"

# 5. Configure CORS on the Bucket
cat << 'CORS' > cors.json
[
  {
    "origin": ["*"],
    "method": ["GET", "PUT", "POST", "DELETE", "HEAD", "OPTIONS"],
    "responseHeader": ["*"],
    "maxAgeSeconds": 3600
  }
]
CORS
gcloud storage buckets update gs://${BUCKET_NAME} --cors-file=cors.json
rm cors.json

# 6. Deploy Backend Service to Cloud Run
gcloud run deploy home-inventory-backend \
  --image gcr.io/${PROJECT_ID}/home-inventory-backend:latest \
  --platform managed \
  --region ${REGION} \
  --allow-unauthenticated

# 7. Deploy Frontend Service to Cloud Run
gcloud run deploy home-inventory-web \
  --image gcr.io/${PROJECT_ID}/home-inventory-web:latest \
  --platform managed \
  --region ${REGION} \
  --allow-unauthenticated
```

## 6. Step-by-Step Migration Guide

### Phase 1: Identity Platform Setup & User Migration
1. **Enable GCIP / Identity Platform**:
   - In GCP Console, navigate to **Identity Platform** (or Firebase Auth connected to the GCP Project) and enable the service.
2. **Enable Auth Providers**:
   - Enable **Email/Password** authentication provider.
   - Configure OAuth Providers: **Google**, **Apple**, and **Facebook** by inputting App Client IDs & Secrets.
3. **Migrate Existing Users**:
   - Retrieve the exact UUIDs (`sub` claims), email addresses, and auth provider details of existing users from Supabase Auth (`auth.users`).
   - For Email/Password accounts, import users using Firebase Admin CLI (`firebase auth:import`) with password hashes (or trigger a one-time password reset link during initial login).
   - Create/link user accounts in GCIP / Firebase Auth using the Admin SDK or CLI, explicitly setting the user `uid` to match their existing Supabase User UUIDs.

### Phase 2: File Storage Migration
1. **Copy Images from Supabase Storage to GCS**:
   - Use `gsutil` / `gcloud storage` or a simple script to copy existing product images from the Supabase `product-images` bucket to `gs://${PROJECT_ID}-product-images`.
   - Maintain the folder structure: `<HomeID>/<ImageUUID>.<ext>`.
2. **Backend API URL Alignment**:
   - Ensure the database references relative paths `<HomeID>/<ImageUUID>.<ext>`.
   - Update frontend image components to prepend the GCS base URL (`https://storage.googleapis.com/${BUCKET_NAME}/`).

### Phase 3: Frontend Containerization & Deployment
1. **Create Dockerfile in Frontend Repo**:
   - Add a multi-stage Dockerfile for Next.js (`standalone` mode enabled in `next.config.ts`).
2. **Setup Cloud Build Trigger for Frontend**:
   - Create a Cloud Build trigger in GCP connected to `https://github.com/Chak-and-Jules/home-inventory-web` for the `main` branch.
   - Configure build steps to build the container image and deploy to Cloud Run.

### Phase 4: Backend Updates for GCIP Token Verification
1. **Update JWT Middleware**:
   - Adjust `internal/middleware/auth.go` to fetch JWKS from `https://www.googleapis.com/service_accounts/v1/jwk/securetoken@system.gserviceaccount.com` (or Firebase Auth issuer `https://securetoken.google.com/<PROJECT_ID>`).
   - Verify token signature, `iss` (issuer), and `aud` (audience = Project ID).
   - Extract `sub` (User UUID) and `email` from claims and set in Gin context.
2. **Add GCS Pre-Signed URL Support**:
   - Use `google.golang.org/api/option` and `cloud.google.com/go/storage` to generate pre-signed upload URLs (`PUT`) in production mode.

### Phase 5: Domain Cutover & Final Verification
1. **Map Custom Domains in Cloud Run**:
   - Map your custom domains to the Cloud Run Frontend and Backend services using Cloud Run Domain Mappings or Cloud Load Balancing.
2. **Verify End-to-End Workflow**:
   - Test login with Email/Password as well as Google, Apple, and Facebook OAuth providers.
   - Verify image uploads and display.
   - Verify all inventory, shopping list, category, and maintenance task APIs.
